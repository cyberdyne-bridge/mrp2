# 光柵化基準（同一份工作負載，同一台 iSH）

畫布 1232×1488（5.5 MB RGB），44 行 × 72 格 = 3168 個字格，每格 12 行。

| 操作 | C (-O2) | Node 22 (V8) | Python 3.12 |
|---|---|---|---|
| clear（整屏填 5.5 MB） | **0.50 ms** | 0.50 ms | 4.13 ms |
| solid（每格滿填 21 B × 12 行） | **0.23 ms** | 82.89 ms | 319.00 ms |
| ink（遮罩 run，約 22% 覆蓋） | 0.46 ms | 55.11 ms | 329.76 ms |

取 20 次最佳值（Python 3 次）。C 用 `memset`，JS 用 `Uint8Array.fill`，Python 用 slice 賦值。

## 讀出來的三件事

1. **C 對 Python：約 1400×**（solid 0.23 ms vs 319 ms）。這個差距不是「優化」，是量級。
2. **Node 不是中間解**：`fill` 對小區塊的呼叫開銷很大，82 ms 只比 Python 快 4 倍，仍比 C 慢 360 倍。JS 只在大塊連續寫入（clear）時跟得上 C。
3. **「只畫墨」在 C 裡也比較慢**（0.46 vs 0.23 ms）：小 `memset` 的呼叫成本 > 省下的頻寬。
   → 少寫像素只有在「頻寬受限」時才有價值（4K、多層合成），文字閱讀器的尺度不成立。

## 結論

渲染器用 C；解析／排版留在 Python（網路 1–2 s 才是大頭）。
協議不動（display list），C 渲染器當獨立進程吃 stdin／socket。
GPU 在這個場景不需要：0.23 ms/幀 只吃掉 60 fps 預算的 1.4%。
